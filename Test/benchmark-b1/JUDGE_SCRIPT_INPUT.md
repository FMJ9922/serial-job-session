# B1 统一审计：脚本输入测量通道指南

本指南仅供六组均已交卷、成果封存后执行统一审计的独立评委使用，不发给开发者。它说明校准环境中实测的输入路径及边界，不增加 B1 要求、分数或指定实现架构，不证明任何参赛功能通过，也不自动完成横向一致性复核。

依据仅为评委校准工程的报告与适配器源码，没有查阅参赛工程。校准 Unity 版本为 **2022.3.62f2**；原输入校准工程报告为 BuiltIn、Old active input handler，同时安装 Input System。因此，不能把结果直接扩展为任意渲染管线、输入后端或游戏逻辑的兼容保证。

## 已验证的路径与适用边界

- **UGUI**：运行中的校准 Button 收到 `pointerDown → pointerUp → onClick → pointerClick`，点击计数从 0 增至 1。适配器通过 `ExecuteEvents` 发送指针事件，让现存事件系统及按钮监听路径处理；这不是直接调用按钮业务回调的许可，也不单独证明屏幕坐标命中、遮挡、布局或物理鼠标输入。
- **IMGUI**：Game View 内部事件及排队事件两种路径都使运行中的 `OnGUI` 消费到鼠标点击和键盘事件，计数分别增加。不能因此宣称同样事件会更新旧版 `UnityEngine.Input` 的轮询状态。
- **新 Input System**：虚拟键盘的 Space 输入使实际 `InputAction` 消费者计数从 0 增至 1。原报告明确记录：这没有带动旧版 `Input.GetKeyDown`。使用时必须确认原游戏的 Action、设备匹配及更新路径实际消费了事件，不能直接执行 Action 的业务回调。
- **旧 Input、有限 KeyCode 替身**：后续独立校准使用 Harmony，仅替换保留键的 `Input.GetKey/GetKeyDown/GetKeyUp` 返回值。运行中原消费者确实读取到一次 down、持续 held、一次 up；经实际 UGUI 改键入口进入捕获，再以合成 F13 触发原捕获代码，绑定由 K 变成 F13。之后 K 仍被原探针读到，但不再驱动已改绑的动作；F13 会驱动动作。该证明限于校准消费者及受限 API，不是对任意旧 Input 游戏的全面覆盖。

旧 Input 校准的保留键仅 **K、F13、F14**；未保留键交回 Unity 原 API。适配器在 `ScriptRunBehaviourUpdate` 之前安装一个 PlayerLoop 提交点，按帧形成 down/held/up 状态；不能把同一帧多次读取误当成多次真实按下。实际证明的是正常运行中的 `Update` 消费者，而不是评委手动增加动作计数。

`string` 重载虽被安装前缀，但没有独立的 string 消费者动态实测；其实现仅尝试将字符串解析为保留的 `KeyCode`，不能据此声称支持任意配置的轴名或按钮名。`Input.anyKey/anyKeyDown`、axis/button API、鼠标、焦点门禁、不同更新阶段及其他输入抽象也未被此校准覆盖。**测量通道不能驱动某 API，不等于参赛功能失败。** 应先为实际输入消费者建立相应测量能力并独立校准；在此之前保留待测状态，不能把通道限制编造成业务失败，也不能直接判通过。

## 统一审计的操作与证据规则

1. 核对当前匿名审计副本、Unity 实例、版本及存档命名空间。仅在审计副本的专用新适配器目录中增加测量代码；不要把本校准的硬编码输出路径、Owner 或键集合直接复制到正在审计的游戏。
2. 先识别原消费者的输入 API、运行状态和正常用户入口。选择适配通道的依据是原程序如何消费输入，不是模型、技能条件或预期得分。六组采用同等证据门槛；不同实现可以使用不同但经验证的输入通道。
3. 测试前保存原业务源码与相关资产哈希；必要时另存原消费者托管 IL 哈希、原 PlayerLoop 和已有 Harmony Owner 清单。使用唯一的审计 Owner，声明实际保留键。不得修改业务源码、预先写入绑定结果、替换存档字段以冒充操作成功、直接调用移动/旋转/暂停等动作方法，或手动增加业务计数。测试夹具设置仍须遵循 B1 对独立算法测试与实际玩家流程的区别。
4. 对 UI 要求，从运行中的现有 UI 事件入口触发；对改键要求，先用 UI 进入原捕获流程，再注入输入让原代码决定绑定。记录原消费者读取、帧号、捕获阶段、前后绑定、旧键及新键的实际业务结果。输入注入成功、按钮存在或显示文本变化，均不能替代所要求的游戏行为证据。
5. 同时验证负向情形：释放后不持续触发；改绑后旧键不再驱动目标动作（除非仍被明确绑定）；非保留键不被替身吞掉。按 B1 原要求验证持久化、取消及冲突处理；这些没有因本次校准而自动通过，也不能要求游戏必须支持 F13/F14 或采用同一种冲突策略。
6. 无论成功、异常、退出 Play Mode 或域重载，都执行清理：撤销本审计 Owner 的全部前缀（校准代码为 `UnpatchAll(Owner)`），恢复原 PlayerLoop，清空合成按键状态。不要卸载其他 Owner 的补丁。记录本 Owner 补丁数归零、循环已恢复及清理后自然输入读数。若游戏本身改变过 PlayerLoop，应在隔离审计进程中处理恢复，避免盲目覆盖原业务新状态。
7. 对照测试前后业务源码/资产哈希与原消费者 IL，确认没有修改或替换业务实现；保存新适配器源码、库哈希、输入轨迹、原消费者状态及 cleanup 证据。Harmony 清理恢复原 API 行为，并不承诺 JIT/native 方法地址逐字节相同。发现业务文件变更则该证据不能作为未修改原交付的通过证明，应回到封存副本重新测量，不能修复业务后再评分。

最终判定仍须对应 B1 的原编号、操作、预期、实测及证据文件；一项多个场景须全部通过才得 1 分。无法测量应先补足测量通道，基础设施问题不得归咎于参赛者。六组全部审计后，另按001–100横向核对同一门槛与证据充分性；分数不同本身不说明标准不一致。

## 视觉与声音证据不能被输入校准替代

原快照中的 `camera.png` 是 **1920×1080 Camera 渲染**，不是包含 Overlay UGUI 或 IMGUI 的实际 UI 截图。它不能证明中文缺字、遮挡、菜单可读性或 B1 第074项通过。UI 视觉验收须捕获实际含 UI 的 Game View/等效完整渲染，并核对分辨率；运行时事件链与 Console 只能支持相应交互事实。

原校准另测得音频输出 RMS 约0.10、静音后0.0，仅证明该校准音源及测量链路；不自动证明参赛游戏的音乐、音效、独立音量和持久化要求。其余视觉、音频与重启项目仍使用 B1 原验收证据。
