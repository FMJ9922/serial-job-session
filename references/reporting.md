# 向人类汇报

日志记录事实，汇报解释事实。没有汇报，人只看到折叠的工具卡片；没有日志，汇报会变成不可核对的记忆。两者都要有，不能互相替代。

## 原则

- 汇报状态变化，不汇报每个工具调用。触发点：任务状态变化、授权/方向/策略变化、有人要等结果、失败/阻塞/未知。
- 先结论，后依据；先影响，后细节。不粘贴 CLI JSON，不复述思维链。
- 事实来自 CLI 输出、`context`、候选和证据；不凭记忆补，不把未发生的验收写成通过。
- 命令成功不等于业务推进成功：先读 `outcomes`；`allowed:false` 是待决，不是完成。
- 失败、阻塞、等待、未知和成功一样要报；不要用沉默重试。
- 语言跟随用户，默认中文。一个状态变化一条；同一 `apply` 多操作合并。
- 长度：例行 ≤6 行，创建简报 ≤15 行，收口 ≤12 行。没有变化就一句“无变化”，不凑字数。
- 有活动任务且操作后仍是非终态时，把同一结论写进 `progress`；终态、创建前、收口后只发对话。
- 写 `progress` 的调用本身不再触发新一轮汇报；`duplicate` 是重试，不是新进展。
- 心跳是漏报补救（约 10 分钟或连续 3 次以上状态变更调用没有汇报），不能替代关键节点。

## 名称与工作层级

任务名称是对人的主称谓，建议用「对象＋预期结果」，例如“恢复原关卡入口与返回重进”。ID 保持稳定，用于定位记录；不能只报“E”或“Stage 23”。开工、切换实施批次、派工、提交、验收和返工，都要让人看懂所属任务名、当前工作名和层级，再说明目标、产物、验收方式及实际状态；相同内容可以合并成一句，不必重复整份合同。

- **正式任务卡**：有稳定 ID、合同、依赖和生命周期；只有对当前合同与候选执行成功的 `accept` 才能称“任务已验收”。正式子任务按 [嵌套](nesting.md) 建卡，并保留父任务验收义务。
- **卡内实施批次**：同一张卡中的一轮具体工作，有可读名称，说明所属卡和当前产物/检查。它没有独立任务生命周期；批次检查通过或证据冻结，不能写成独立任务 `accepted`。
- **候选版本**：一次 `report` 提交的产物版本，用于绑定评审；编译次数、源码快照和证据目录编号不等于候选版本。
- **返工次数**：按实际 `reject` 和日志预算计算；切换批次、重命名工作、重新编译不能重置或虚增返工次数。

历史只有字母或 Stage 时，通过现有 `parameters` 和 `progress` / `knowledge` 追加可读显示名、所属任务及历史别名对应关系；不用新增 schema 字段或改写旧 `title`、ID、路径和事件。恢复时按实际任务 ID 解析对应映射，不把继承来的父卡显示名当作子卡名称；旧编号仅在需要定位历史证据时附注，不把所有旧批次追造为任务卡。命名整理不改变合同、依赖、预算和验收状态，也不替代正式合同变更。

例如某张“恢复原关卡入口与返回重进”的卡内，历史 Stage 20–23 是连续实施批次，应这样汇报：

```text
【进度】任务「恢复原关卡入口与返回重进」仍在执行
- 当前工作：卡内批次「统一四份配置表版本与发布链」（历史 Stage 23）
- 目标/产物：补齐版本清单与发布链，提交可追溯的配置产物
- 验收/状态：检查版本一致性与发布链接；目前只完成部分修改，整卡尚未验收
- 下一步：补齐检查证据后提交候选
- 需要你：无
```

“Stage 23 已完成，所以任务已验收”或“已从 E 推进到 W”都不足以披露业务进展。应使用名称，并分别交代批次检查结果和正式任务状态。

## 四段格式

```text
【进度】一句话结论
- 依据：任务 ID/标题、候选版本、证据路径
- 下一步：具体动作
- 需要你：问题或「无」
```

有风险/未知时加一行 `- 风险/未知：...`。开工前用「我要做什么 + 边界 + 验收」；完成后用「做了什么 + 结果 + 下一步」。不要只写“完成了”。

状态标记保持少而稳定：`【创建】`、`【进度】`、`【派工】`、`【受阻】`、`【完成】`。需要人类动作时，最后一行必须是 `需要你：...`；不需要时明确写 `需要你：无`（全 AI 模式下写“无（全 AI 模式，继续）”）。

## 检查点

`progress` 能不能写，看操作后的实际状态：`accepted` / `failed` / `cancelled` 是终态，不写；`ready` / `doing` / `awaiting_acceptance` 可写。`reject` 可能回到 `doing`，也可能耗尽返工变 `failed`，按结果判断。

| 触发 | 时机 | progress | 必须包含 |
|---|---|---|---|
| `init --dry-run` | 预检后、正式创建前 | 否 | 创建简报 + 一个确认问题 |
| `init` | 创建成功后 | 否 | 实例路径、route_key、模板版本、下一步 |
| `create` | apply 后 | 可写 | 每张卡的 ID/标题、父子/依赖、required、先做哪张 |
| `start` | 开工前后 | 看结果 | 合同目标、授权、必验项、谁执行；`allowed:false` 时写原因和需要人做什么 |
| 派发/恢复 agent | 派发前、返回后 | 看结果 | 角色、任务、边界、验收、预期回报、等待方式 |
| `report` | 候选提交后 | 可写 | 候选版本、摘要、证据、下一步 reviewer |
| `assess` | 评估后 | 可写 | 结论/评分/风险/未知/证据；不把建议当决定 |
| `accept` | 成功后 | 否 | 结论、验收版本、证据、下一步 |
| `accept` 被拒 / `allowed:false` | 后 | 可写 | 未推进、原因、待决项；任务仍在 `awaiting_acceptance` |
| `reject` | 后 | 看结果 | 返工原因、剩余次数、保留成果；回到 `doing` 才写 progress |
| `fail` / `cancel` | 后 | 否 | 原因、已尝试动作、保留成果、恢复方式、需要人做什么 |
| `nest` | 拆分前后 | 可写 | 收益/成本、任务树、依赖、父任务验收门 |
| 方向/策略/参数 | 变化后 | 可写 | 改了什么、为什么、影响哪些任务 |
| `handoff`/恢复 | 恢复前后 | 视任务 | 北极星、当前卡或菜单、上次 progress、下一步 |
| 停止/收口 | 结束时 | 否 | 已交付/失败/阻塞、证据、经验、恢复方式、待决 |

## 模板

### 创建简报

```text
【创建】串行任务「<route_key>」
- 北极星：<用自己的话复述目标>
- 成功标准：<总目标或首张任务的必验项；尚未确定就写“首张任务合同时确定”>
- 范围：workspace=<...>；实例=<...>；route_key=<...>
- 授权：paths=<...>；tools=<...>；资源=<...>
- 模式：<manual/conditional/full_ai；conditional 写三个阈值和风险上限>
- 失败：最多返工 <N> 次；耗尽后 <skip/stop>
- 模块：估分 <开/关>；飞书 <开/关>
- 预算/时限：<有就写，没有写“无”>
- 模板/版本：<version>
- 需要你：确认创建？要改哪一项？
```

默认值和显式值分开标；任何可能让人意外的项（全 AI、`on_failure=skip`、宽授权路径、共享资源）要单独点出来。用户已明确回答的项目不重复问。

### 建任务

```text
【进度】已创建 <N> 个任务
1. 1「研究参考」→ 2「实现」→ 3「实机验证」
- 1 就绪；2 依赖 1；3 依赖 2（required）
- 先做 1；合同：<goal>；必验：<checks>
- 需要你：无（manual 模式下开工前会再确认）
```

### 开工

```text
【进度】开始任务 2「实现登录页」
- 合同：<goal>
- 授权：<paths/tools/resources>
- 必验：视觉对齐、交互回归、无控制台错误
- 执行：worker-ui（本会话/新建）
- 下一步：实现后自检，提交 candidate-1
- 需要你：无
```

`allowed:false` 时：

```text
【受阻】任务 2「实现登录页」未开工
- 原因：<decision.reason；例如等待人工批准、评估缺失、阈值未达>
- 状态：仍为 ready
- 下一步：<补齐评估/请你批准/按策略转人工>
- 需要你：<具体决定或「无」>
```

### 派工（派发前 / 派发后 / 返回后）

派发前：

```text
【派工】reviewer-2 → 任务 3「登录页视觉对齐」候选 candidate-1
- 为什么是它：独立 reviewer，未参与实现，当前会话无冲突
- 边界：只读 src/ui/**，不改文件；不碰任务 1 的产物
- 验收：合同 v1 的三项必验项，每项需证据路径
- 预期回报：结论 + 逐项证据 + 未知项 + 限制
- 我接下来：等它回报后汇总，再决定 accept 或返工
```

派发后：

```text
【派工】已派发 reviewer-2；它正在核对 candidate-1。
- 我同时：整理候选证据，准备验收摘要
- 预计：收到回报后先汇总，再给你一个 accept/返工建议
- 需要你：无
```

返回后：

```text
【进度】reviewer-2 已返回：结论 <pass/blocking/uncertain>，风险 <low/medium/high>
- 必验：<逐项 passed/failed/unknown + 证据路径>
- 未知：<列出；没有写“无”>
- 下一步：<accept / 返工 / 转人工>
- 需要你：<决定或「无」>
```

### 候选提交

```text
【进度】任务 1「修复目标界面」已提交 candidate-1
- 摘要：<一句话>
- 证据：<路径1>、<路径2>
- 贡献者：<worker>
- 下一步：送独立 reviewer 验收
- 需要你：无
```

### 验收 / 返工 / 失败 / 阻塞

```text
【完成】任务 1「修复目标界面」已验收 candidate-1
- 必验：三项全部 passed；证据 <路径>
- 评分/风险：<score / risk>
- 下一步：<下一个 ready 任务/收口>
- 需要你：无
```

```text
【进度】任务 1「修复目标界面」返工：<reason>
- 失败项：<check id + 证据>
- 剩余返工：<N>
- 下一步：<谁去改、改什么>
- 需要你：<决定或「无」>
```

```text
【受阻】任务 2「导出修复」未开工
- 原因：<缺少 Unity 实例；资源被任务 1 持有>
- 已尝试：<动作；没有就写“尚未尝试”>
- 下一步：<任务 1 验收后重试 / 跳过 / 停止>
- 需要你：<关掉编辑器或授权等待/跳过>
```

### 方向、拆分、策略、参数

```text
【进度】方向建议：<route>
- 备选：<候选路线 + 理由>
- 风险/未知：<...>
- 下一步：<按模式决定/请你选>
- 需要你：<选择或「无」>
```

```text
【进度】已拆分任务 2「实现登录页」
- 2/1「研究参考」→ 2/2「实现」→ 2/3「实机验证」
- required：全部；2 验收前必须等 2/1–2/3 accepted
- 下一步：先做 2/1
- 需要你：无
```

策略/参数变化：说明改了什么、为什么、影响哪些任务、是否需要人批准；不要只说“已更新”。

### 恢复 / handoff

有当前任务：

```text
【进度】恢复：北极星 <goal>；当前任务 2「实现登录页」（doing）
- 上次进展：<progress.summary>
- 待决：<questions/decisions；没有写“无”>
- 下一步：<继续实现/送审>
- 需要你：<决定或「无」>
```

没有当前任务（ready 等开工、上一卡刚结束、失败后重启）：

```text
【进度】恢复：北极星 <goal>；当前没有进行中的任务
- 状态：<例如任务 2 ready 等你批准；任务 1 failed；所有任务已验收>
- 可选卡：<ID/标题/状态/阻塞原因>
- 下一步：<请你选 / 按模式选 / 先处理失败>
- 需要你：<选择任务或处理方式>
```

需要某张 ready/failed 卡的历史进展时，显式 `context --task-id <ID>`；不要假设默认 `context` 会带回它。

### 收口

```text
【完成】本轮收口：<route_key>
- 已交付/已验收：<任务名称 + ID + 版本>
- 未完成/失败/取消：<任务名称 + ID + 原因 + 保留成果>
- 证据：<关键路径>
- 经验：<knowledge id 或“无新增”>
- 恢复：说 route_key：意图，或运行 context --view recovery --instance <路径>
- 需要你：<待决项或「无」>
```

## 错误与边界

- `DECISIONS_REQUIRED`：创建参数缺失，不是普通失败。把 `missing` / `choices` / `suggestions` 逐项问人；建议值不是确认值；不要自行选默认，也不要原样重试。
- `TEMPLATE_CHANGED`：共享方法升级。先说明变化、旧实例影响和需要确认的 rebind；得到真实人类确认后才 `rebind_template`；不要静默重绑。
- `TASK_NOT_ACTIVE` / `TASK_NOT_READY` / `REVISION_CONFLICT`：先读 `context` 说明当前状态和 revision，再决定下一步；不要反复硬重试。
- 超时/提交未知：先 `context`/`check` 核实是否已提交，再决定是否重试；向人说明不确定性。
- `duplicate`：原命令的重试，不是新进展；不写 progress、不重复汇报。
- 只含 `progress` 的 apply：不触发第二轮汇报；确认内容与刚说过的一致即可。
- 混合 apply：只汇报实际业务变化；不要把“写入 progress”本身当成新成果。
- 全 AI：汇报是 FYI，末尾写“需要你：无（全 AI 模式，继续）”；只有授权/预算/阻塞/失败才要求决定。
- 用户豁免确认：只认同一会话里的明确人类指令；创建后补完整简报；agent 不得自行豁免。
- 压缩/重启：先 `context`/`handoff`，复述北极星、当前卡或菜单、上次 progress，再继续。
- 敏感信息：不粘贴密钥、凭据、完整私有路径；用证据路径和任务 ID 指代。
- 终态任务：不能再写 `progress`；结论以生命周期事件为准。需要可复用的恢复摘要时写有证据的 `knowledge`，不要伪造 progress。
- 没有证据/未知：如实写“无新证据/未知”，不要用评分或汇报掩盖。

## 反例

- “已完成。”——没有对象、结果、证据、下一步。
- 把 `init --dry-run` 的 JSON 直接贴给人——人需要的是简报和确认问题，不是配置对象。
- 命令成功就写“已开工/已完成”——`allowed:false` 时任务仍是 ready；先读 `outcomes`。
- 失败后静默重试三次——人不知道发生了什么，也无法决定跳过/停止。
- 每次工具调用都发一条——刷屏会让人停止阅读；按检查点合并。
- 把思维链当汇报——人要的是结论、动作、证据、下一步。
- 只报成功，不报未知和保留成果——验收会建立在错误印象上。

## 与日志的关系

- `progress` 是“人最近被告知什么”的持久记录，也是 handoff 的恢复点；`summary` 要一句能看懂的话，`questions` / `decisions` / `next_steps` 是可执行项。
- 终态、创建前、收口后不写 `progress`；这些场景用对话，必要时用 `knowledge`。
- 汇报不能改写事实：日志、候选、评估和证据仍是权威；汇报只是把它们翻译给人。
