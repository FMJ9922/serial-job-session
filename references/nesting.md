# 内置嵌套工作流

复杂任务可以先说明拆成子任务的收益、额外成本和依赖，再用 `nest` 记录理由。人工主导等待确认；条件自治按当前可行性评估与确认门槛判断；全 AI 在授权与预算内自行决定。

子任务仍用 `create`，增加 `parent_id`；可用 `parent/child` 作为 ID，但这只是数据标识，不是目录。所有层级共用 run、state 和两条日志。不复制 skill，不创建嵌套实例或每卡文件。

默认最大嵌套深度2层（顶层深度0）、每个父任务最多8个直接子任务，可在创建配置 limits 中调整。父任务必须 doing 且已授权 nest。子任务继承父任务的策略、路径、工具和资源，只能缩小授权；提高策略权限须人确认。

默认 required=true。必需子任务全部 accepted 后才可验收父任务；failed/cancelled/unknown 都不能充当通过。子任务可有兄弟依赖；必须先验收依赖，再开工。禁止依赖自身、祖先或产生包含父子完成关系的环。

父任务 report 前也检查必需子任务；尚未完成时直接拒绝，父任务保持 doing，避免提前进入待验收后阻塞子任务。父任务验收通过时取消仍未结束的可选分支并保留其成果。父任务失败或取消时，同样取消未结束的后代，释放资源。

必需子任务耗尽返工后失败或被取消时，父合同已无法完成，父分支标记 failed 并保留成果，未结束的兄弟分支取消；按失败策略停止或继续独立任务。可选子任务失败不使父合同失败。宿主须协作停止相关 worker，日志状态变化不会强杀编辑器或进程。

例如把界面改造分成“研究参考 → 实现 → 实机验证”，每个节点只交付一个合同。只有独立写入范围和资源的节点可并行；资源锁及并发预算统一由编排器管理。拆分不会扩大授权、自动增加预算或减少父任务必验项。

在同一个 apply 命令中可以先 nest，再依次 create 子任务，或先 create 前置，再 create 依赖它的任务。整条命令验证成功后写一条日志；失败则全部不写。
