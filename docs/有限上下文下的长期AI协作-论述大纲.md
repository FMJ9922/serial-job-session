# 有限上下文下的长期 AI 协作：从商业交付需求到 serial-job-session

本文为文章大纲，供后续逐节扩写与打磨。

**核心命题：长期 AI 协作需要让目标、决定、工作状态和验收责任跨越步骤与会话持续有效。serial-job-session 从自身商业交付需求出发，将具体的专业工作方法固化为通用 AI 工具能够执行、检查和持续承接的协议。外部持久状态、任务合同和持续验证是它采用的工程路径；它在目标场景中是否比通用默认用法更合适，以及收益能否覆盖过程成本，需要由实际运行判断。**

全文围绕“实际问题 → 工作连续性的要求 → 专业方法的定制 → 机制如何落实 → 适用边界与效果验证”展开。当前重点是解释现有设计的理由，不提出功能升级路线，也不预设它优于其他方案。

## 一、从局部高效到长期交付：问题如何出现

从实际使用体验出发：AI 可以快速完成局部实现，但工作持续数天、数周，经历多次返工和会话交接后，维持方向与判断完成状态逐渐成为主要负担。

明确“长期”的关键含义：后续步骤依赖前面形成的决定、产物和验收状态。这种依赖可能跨越会话、执行者和工具；即使只有几个步骤，也可能遇到连续性问题。持续很久的一批独立任务，则未必具有同样的困难。

展开几个典型现象：

- 需要反复解释背景、约束和之前的决定。
- AI 记住了近期任务，却逐渐偏离最初目标。
- 实现、尝试、推测和已验证事实混在一起。
- 局部任务不断完成，整个项目是否接近交付却难以判断。
- 人逐渐承担起外接记忆、调度和核验工作。

本节提出全文的问题：**如何让局部执行能力，持续服务于一个长期目标？**

## 二、上下文限制如何转化为工程问题

先区分三个概念：信息处理速度、单次上下文容量，以及跨阶段维持有效工作状态的能力。说明模型读写速度很快，并不自动意味着它能长期保持项目理解。

然后讨论三个相互关联的困境：

- **架构困境：** 当前改动可能依赖分散在不同阶段、模块和决策中的信息。
- **协作困境：** 人需要不断补充背景、纠正理解，并跟上 AI 产生的变更。
- **验收困境：** 产物生成加速以后，正确性、完整性与实际效果仍然需要证明。

保留原文章对问题的洞察，同时避免依赖“人脑相当于多少 token”“项目构思有多少 MB”等难以验证的量化推断。

论证时区分“信息是否放得下”“模型能否有效使用信息”和“哪些信息仍然有效”。上下文容量只是其中一个条件；状态识别、关联判断与验证能力也会影响结果。

## 三、一个基本判断：长期工作需要可持续的外部组织

说明项目的全部信息不必始终同时存在于一次上下文中，但每次工作都需要获得足够的相关信息，并能把结果可靠地交给下一阶段。

据此提出设计思路：

> 将目标、约束、决策、任务状态和验证结果保存在会话之外，让每次会话围绕明确范围工作，并把新增事实交还给持续存在的项目记录。

同时明确：外部存储只是基础，还需要规定记录什么、何时更新、如何恢复，以及什么条件下可以继续推进。

区分历史记录与当前工作依据：保存过的提议、失败尝试和过期结论，不应仅因为能够被检索就被当作当前事实。持久记录与按需读取需要配合，避免将全部历史重新灌入上下文；选择不当和维护不及时也可能带来干扰与成本。

## 四、为什么定制 skill：将自身专业方法接入通用工具

介绍它面向的场景：跨天、跨周、反复交接与返工的 AI 辅助商业交付。

先说明通用工具与定制方法的目标差异。通用 CLI 需要适应不同用户、项目与任务，默认流程难以预先规定每个团队的合同粒度、评审要求、风险偏好和完成标准。这里不把差异简单归因于“照顾新手”或“专业能力不足”；不同专业团队也需要不同流程。

自写 skill 的价值，是把实际工作中的明确选择交给工具反复执行：愿意为哪些风险增加检查，什么情况下必须独立评审，哪些失败必须保留，何时自治、何时由人决定。专业性体现在这些选择与场景的匹配，也体现在知道哪些步骤可以省略。

据此给出项目定位：

> 将面向自身商业交付需求的工作方法，固化为通用 AI 工具能够执行、检查和持续承接的协议。

再阐述支撑这一定位的设计原则：

- **方法与事实分离：** 共享 skill 保存工作方法，项目实例保存参数与执行事实。
- **关键状态持久化：** 工作能否续接，不完全依赖聊天历史和压缩摘要。
- **结论区分层次：** 提议、执行、候选、验收与失败具有不同含义。
- **变化保留依据：** 允许修订方案，同时留下原因与历史。
- **参与程度显式约定：** 人工主导、条件自治和全 AI 对应不同决策方式。
- **控制过程开销：** 只为值得独立管理和验收的工作建立正式任务；依赖少、结构简洁是设计选择，实际使用是否轻量仍需观察。

本节回答：为什么需要这套定制方法，以及为什么采用这组机制。定制化提供更贴合需求的可能性，效果优势仍需验证。

## 五、从目标到验收：工作如何被组织起来

作为全文的主体，按照一次工作的生命周期展开。

1. **建立共同起点。** 明确目标、成功标准、范围、授权、预算和失败处置。
2. **形成任务合同。** 在实施前说明交付物、依赖和必验项，让“完成”有稳定含义。
3. **按有限上下文执行。** 给执行者提供当前合同、相关依赖、反馈和恢复信息，按需读取证据。
4. **提交候选并评审。** 将实现结果与合同版本、候选版本和证据引用关联；评审者按合同检查实际产物，证据引用本身不等于证据已被核实。
5. **处理返工与失败。** 保留失败事实和已有成果，按预算决定重试、停止或继续独立任务。
6. **交接与恢复。** 新会话从持久状态恢复目标、当前进展、未决问题和下一步。

用一个贯穿示例连接这些步骤，例如：一项持续两周、途中需要更换技术路线的系统迁移。

突出这套规则的具体关注点：除了决定下一步做什么，还要明确一个结果凭什么被接受、能否供后续步骤依赖。

## 六、方向可以变化，交付责任如何延续

专门讨论长期工作最容易出现的偏移：原方案失败后，任务被重拆、目标被重新表述，原本困难的验收要求随之消失。

说明本设计如何约束这种变化：

- 方向调整先记录依据、备选方案和未知项。
- 合同与候选都有版本，变更后重新判断有效性。
- 新候选不能直接继承旧候选的验收。
- 必验项的失败与未知不能被总体评分抵消。
- 重规划时明确承接尚未完成的验收义务。

本节突出一个核心思想：**长期可靠性需要让尚未履行的责任跨越方案变化和会话边界。**

准确区分实现层次：合同与候选版本绑定、状态合法性和必验项记录由 CLI 检查；重规划后的合同是否在语义上完整承接原义务，仍依赖 agent 或人的判断与协议执行。不能将后者表述为已经实现的自动证明。

## 七、人和 AI 如何在这套机制中协作

解释三种决策模式分别适合怎样的参与方式，以及授权、执行和验收之间的关系。

明确“全 AI”表示在约定授权与预算内由 agent 作出决策，不构成成功率或无人监督交付质量的承诺。自主执行也可能以失败、阻塞或未完成结束；这些结果必须如实记录，不能通过降低验收标准换取完成。

进一步说明：

- 日志服务于恢复和追溯，简报帮助人理解进展并作出决定。
- 角色分工明确责任，独立评审提供额外检查机会；实现贡献者与 reviewer 身份分开，不代表二者的错误在统计上独立。
- agent 的具体创建、复用和执行依赖宿主能力。
- 人仍然可以提供领域知识、取舍与品味判断；插件帮助这些输入持续约束后续工作。

本节回答：它如何减少人反复交代和追账的负担，又如何保留必要的人类参与。

同时说明运行边界：CLI 约束通过它提交的控制状态；宿主的实际工具操作、身份来源真实性与权限执行仍有各自责任。日志可重建不等于外部操作可以安全重放，来源记录也不等于安全鉴权。

## 八、已有实践中的位置与实际效果的判断

### 与相关方案的关系

说明外部状态、任务合同、状态机与独立评审已有相邻实践。相关工作用于交代设计背景和比较对象，不以“市场独有”作为项目存在的前提。

- 通用运行时提供持久执行、恢复与人工介入等基础能力，应用者仍需定义具体的交付规则。能够用框架搭建某套方法，不等于安装框架后就已经获得这套方法。
- 提供具体长期工作流程的 harness 与系统，则是更直接的比较对象，不能仅靠“框架与 skill 分层不同”回避效果和成本比较。
- 本项目的辨识度来自规则组合及其适用方式：合同与候选的版本绑定、失败与未知的保留、验收义务延续、参与模式，以及接入现有宿主的方式。这些是设计侧重点，不是排他性创新声明。

扩写时可采用的相关材料：

- [Anthropic 长期 agent harness 实践](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)：交代持久进度、功能清单与跨上下文增量推进的工程背景。
- [LangGraph 官方定位](https://docs.langchain.com/oss/python/langgraph/overview)：说明运行时基础能力与具体工作规则之间的关系。
- [AstronOS 原论文](https://arxiv.org/html/2608.16381v1)：讨论跨步骤状态依赖、候选与已接受状态、版本化交接。其实验限定于受控的软件更新计划任务，不能直接推及完整软件交付。
- [Agent Behavioral Contracts](https://arxiv.org/abs/2602.22302)：作为合同与运行时约束的相关研究，其形式化保证不能直接移植到本项目的自然语言任务合同上。
- [DeliverBench](https://arxiv.org/abs/2611.03412)：支持局部任务表现与最终项目交付需要分别评估的问题意识，不作为本项目有效性的证明。

### 区分机制、相邻证据与自身效果

明确三层判断：仓库当前实现了什么；相邻研究对某些设计假设提供了什么信号；本项目在实际使用中改善了什么。前两层不能替代第三层，同行实验的数字应保留任务范围、比较条件与成本背景。

可以从机制解释的作用包括：

- 关键事实有外部载体，交接可以有据可依。
- 完成状态受到合同、版本和必验项约束。
- 失败、未知与未完成义务可以持续保持可见。
- 人的参与方式和决策边界可以提前约定。

实际需要观察的效果包括：

- 换会话后是否更容易恢复有效工作。
- 是否减少重复解释、遗漏要求和方向偏移。
- 是否提高最终交付质量。
- 为此增加了多少流程、时间与维护成本。

同时写明边界：记录不能自动证明证据真实，独立 reviewer 不能保证判断正确，局部验收通过不能自动证明整体体验优秀。

评估基线优先贴近自身选择：在同类任务和可比条件下，与通用工具默认用法或现有工作方式比较。必要时再与相近方案比较，不能仅凭功能列表判断优劣。

讨论适用条件与成本：要求越难明确、越频繁变化，建立和维护合同通常越需要判断；可检查性、任务风险、协作规模都会影响流程收益。简单一次性任务未必值得引入整套协议。

本节无需提出新功能。先观察现有设计在实际任务中的表现，再决定是否调整方法；既不预设全面优于成熟框架，也不因通用框架能实现类似机制就否定它的用途。

## 九、结语：让长期工作具有连续性

回到出发点：AI 的局部能力已经可以创造价值，长期工程还需要一种持续承接目标、事实、决策和责任的组织方式。

通用工具提供广泛能力，专业使用者可以通过定制 skill 将自己的工作要求落实为可重复执行的方法。项目的存在意义来自它对真实需求的适配，进一步的效果主张则需要实际证据。

以审慎的主张收束全文：

> serial-job-session 从自身商业交付需求出发，尝试让有限上下文中的一次次执行，形成可以恢复、可以追溯、具有明确验收依据的连续工作。它需要回答的是：在所关心的工作中，这套专业方法是否比通用默认用法更合适，以及收益是否值得付出的过程成本。
